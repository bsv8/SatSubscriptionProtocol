# SSP 身份与长连接边界设计

## 1. 设计目标

SSP 是运行在已认证长期连接之上的业务协议。实际部署使用
`/home/david/Workspaces/bitcoin-libp2p` 建立和维护连接，但 SSP 仓库不引入、封装或适配
bitcoin-libp2p。

```text
外部 bitcoin-libp2p 应用
  ├── 建立和维护长期连接
  ├── 认证远端长期公钥
  ├── 处理加密、分帧、超时、断线和实际发送
  └── 向 SSP 交付 remote_public_key + 完整 SSP Wire
        └── SSP SDK
              ├── 严格解析 Wire
              ├── 更新或查询订阅状态
              └── 产生直接响应或广播事件
                    └── 交回外部应用发送
```

SSP 不自行建立连接、不认证身份、不管理在线连接，也不处理支付。

## 2. 统一输入

外部应用完成连接认证后，只向 SSP 交付：

```go
type AuthenticatedPayload struct {
    RemotePublicKey PublicKey // 从已认证长期连接取得的远端公钥
    Payload         []byte    // 一个完整 SSP Wire
}
```

SSP 服务入口：

```go
HandleMessage(ctx, remotePublicKey, payload, backend, dispatcher) (
    responsePayload, hasResponse, error,
)
```

订阅集合使用 `remote_public_key` 标识。SSP payload 不能声明或覆盖这个身份。

## 3. 身份边界

- `remote_public_key` 必须来自外部 bitcoin-libp2p 已认证连接。
- SDK 只检查其为 33 字节且以 `02/03` 开头的压缩公钥字节形状，不验证 secp256k1 曲线点；
  真实公钥认证由外层长期连接完成。
- 不能相信 SSP payload、展示字段或普通调用参数自报的身份。
- SSP Wire 不携带公钥和签名，不重复长期连接已经完成的认证。
- 订阅持久化以已认证公钥 exact bytes 作为 key。
- SSP Publish 不包含原始发布者公钥；SSP 不提供发布者身份证明能力。
- 一个公钥代表一个长期订阅身份。SSP v1 不定义 `session_id` 和多会话合并。

身份认证失败发生在进入 SSP 之前，不属于 SSP 协议错误。

## 4. 长连接调用契约

外部 bitcoin-libp2p 应用负责从长期连接读取完整 SSP Wire，并按该连接的接收顺序串行
调用 SSP：

```text
长期连接收到 Wire
  → 取得该连接已认证的 remote_public_key
  → HandleMessage(remote_public_key, wire, backend, dispatcher)
      ├── 无直接响应：Publish / Subscribe / Unsubscribe
      └── 直接响应：SubscriptionsResponse
  → 外部应用把直接响应写回原连接
```

规则：

- Subscribe 和 Unsubscribe 成功时没有 SSP 响应 Wire。
- SubscriptionsRequest 成功时，外部应用把 SubscriptionsResponse 写回同一连接。
- 同一连接按顺序处理，因此列表响应反映此前已成功处理的订阅操作。
- SSP 不定义连接握手、Stream Protocol ID、分帧、长度前缀、心跳或重连。
- SSP SDK 只检查自身 Wire 上限；外部应用可以设置更严格的连接限制。

## 5. 广播输出契约

收到 Publish 后，SSP 服务把下列广播事件交给抽象 Dispatcher：

```text
authenticated publisher public key
channel
content_json exact bytes
完整 Publish Wire exact bytes
```

Dispatcher 是依赖倒置接口，不是 bitcoin-libp2p 适配器。外部应用负责实现它，并使用自己
的在线连接注册表完成实际发送。

SSP SDK 提供规范的订阅集合状态转换、排序和 `Matches(subscriptions, channel)` 纯函数。
外部 Dispatcher 必须使用该规则保证：

- 普通订阅精确匹配 channel；
- `["*"]` 匹配所有普通 channel；
- 同一订阅身份对一条 Publish 最多交付一次；
- Publish 的 channel、JSON exact bytes 和完整 Wire 不被改写。

在线连接选择、慢消费者、backpressure、写入超时和连接清理由外部应用负责，不进入 SSP
SDK。

## 6. 顺序、断线和重试边界

SSP 不定义 `request_id`、`sequence` 或 `expires_at`。

- 同一条长期连接中的 SSP Wire 按外部应用交付给 SDK 的顺序处理。
- 订阅状态按长期公钥持久化，断线不删除订阅集合。
- SSP 没有历史、离线队列、确认或补发。
- 断线期间的 Publish 不会在重新连接后补发。
- Subscribe 和 Unsubscribe 是幂等操作，可以安全重试。
- Publish 不是幂等操作；外部应用重复交付同一 Publish 会产生重复广播。
- SSP 不定义跨连接或跨发布者的全局消息顺序。

## 7. SPI 与计费边界

外部应用可以对同一 `remote_public_key` 使用 SPI，并据此决定是否把一次操作交给 SSP：

```text
已认证 remote_public_key + SSP Wire
  → 外部应用的 SPI / 计费策略
  → HandleMessage(remote_public_key, SSP Wire, backend, dispatcher)
```

规则：

- SSP payload 不携带 SPI payload。
- SSP 不携带价格、余额、支付地址、支付证明或有效期。
- SSP SDK 不调用 SPI，也不依赖 SPI SDK。
- 计费拒绝由外部应用处理，不定义 SSP 计费错误 Kind。
- 更换计费方式不改变 SSP Wire 和订阅集合语义。

## 8. 明确不实施

SSP 仓库不实施：

- HTTP 身份外壳或 HTTP 请求处理
- WebSocket、WebRTC 或 bitcoin-libp2p 适配器
- bitcoin-libp2p 依赖、Stream handler 或连接注册表
- 网络分帧、握手、加密、心跳、重连、超时或 backpressure
- 真实网络发送和在线连接生命周期

这些能力由使用 `/home/david/Workspaces/bitcoin-libp2p` 的外部应用负责。

## 9. 错误边界

- 连接认证失败、分帧错误、断线或发送失败：外部 bitcoin-libp2p 应用错误。
- SSP Wire 格式错误、非法 channel、无效 JSON：SSP 协议解析错误。
- 订阅 Backend 失败：SSP 服务实现错误。
- Dispatcher 回调失败：SSP 调用错误，实际连接处理由外部应用决定。
- SPI 余额不足或计费策略拒绝：外部应用策略错误。

SSP v1 不定义 ErrorResponse。SDK 只把稳定的本地错误返回给调用者。
